# AlarmKit investigation session log

- 2026-08-01 14:05 PKT: Read the required writing rules and inspected Super Alarm's product spec and iOS implementation. The product requires a recurring morning wake alarm and does not consider the alarm dismissed until the user scans an allowed QR spot or enrolled object.
- 2026-08-01 14:12 PKT: Verified Apple's current AlarmKit documentation and WWDC25 session. AlarmKit supports one-time and weekly repeating alarms, custom sounds, system-managed prominent alerts that break through Silent Mode and Focus, separate per-app authorization through `AlarmManager`, and the `NSAlarmKitUsageDescription` Info.plist key. Apple's setup does not use the Critical Alerts notification entitlement.
- 2026-08-01 14:16 PKT: Confirmed from Apple's AlarmKit API documentation and the installed Xcode 26.6 iOS 26.5 SDK that `AlarmPresentation.Alert` always has a system-provided stop control. `stopIntent` is an action run when that control is tapped; the API exposes no conditional stop or replacement dismissal flow that can require a QR/object scan.
- 2026-08-01 14:20 PKT: Decision: AlarmKit can replace Critical Alerts for the iOS 26+ alarm-delivery layer, but it cannot serve the full Super Alarm product because its system stop control bypasses the required scan gate. Keeping iOS 16-25 support also requires a separate local-notification fallback, for which Critical Alerts would remain relevant if Silent Mode and Focus bypass are required.
- 2026-08-01 14:27 PKT: Rechecked Apple's AlarmKit action model for a scan handoff. A custom secondary button can run a `LiveActivityIntent` with `openAppWhenRun = true`, allowing Super Alarm to open its scanner. Apple's session also says custom intents can be attached to the stop button, but the system still owns the alarm lifecycle; this supports a scan prompt, not a guaranteed scan-before-stop gate.

- 2026-08-01 20:52 PKT: Deepened the Stop analysis with Apple's current AlarmKit scheduling documentation, AlarmKit API reference, WWDC25 session, and Apple DTS FAQ. The system-provided Stop action genuinely stops the currently alerting AlarmKit alarm; `stopIntent` runs afterward as an App Intent callback and cannot veto or condition that transition. Apple DTS also states that a physical button reaction stops currently alerting alarms. AlarmKit alarms persist across app force-quit, crash, and reboot, but the public API does not expose a conditional dismissal gate or an unbounded alert-duration control.
- 2026-08-01 20:52 PKT: Compared shipped mission-alarm products and a July 2026 AlarmKit implementation report. The strong pattern is layered rather than escape-hatch removal: AlarmKit supplies the resilient system trigger; a `LiveActivityIntent` with immediate foreground mode hands control to the app; the app owns mission state and can resume playback with `AVAudioSession`; pre-scheduled follow-up AlarmKit alarms re-ring after Stop, force-quit, or unfinished scanning; exact QR/barcode matching, lock windows, and wake-up checks add behavioral friction. The implementation report describes a chain of 15 alarms two minutes apart, canceled only after mission success, and removes snooze because it conflicts with that chain.
- 2026-08-01 20:52 PKT: Recorded the product boundary: Super Alarm can provide a strong gate where Stop silences this occurrence but does not clear the wake mission. It cannot provide a hard gate where the system Stop is unavailable or impossible before a valid scan. Current products such as BarLock and ZzZlapp market the layered approach, while Rouse explicitly acknowledges that public iOS 26 AlarmKit apps cannot truly force a mission. Backup chains need device testing because AlarmKit can return `maximumLimitReached`, and dense chains have reported timing reliability issues on some locked-device conditions.
